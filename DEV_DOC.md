# Developer Documentation

This document describes first-time environment and secret setup, architecture, implementation, and maintenance of the Inception infrastructure.

For daily commands, local-domain mapping, access, and reset guidance, see [USER_DOC.md](USER_DOC.md). For the project introduction, concise design summary, resources, and AI-usage disclosure, see [README.md](README.md).

## Architecture

The infrastructure is a Docker Compose project composed of three mandatory services:

```text
Host browser
    │ HTTPS :443
    ▼
NGINX
    │ FastCGI over the private Docker network
    ▼
WordPress + PHP-FPM
    │ MariaDB protocol over the private Docker network
    ▼
MariaDB
```

NGINX is the only host-facing service. It accepts HTTPS requests and forwards PHP processing to WordPress/PHP-FPM. WordPress connects to MariaDB over the internal Docker network. MariaDB and WordPress are not intended to be published directly to the host.

The stack is orchestrated through `srcs/docker-compose.yml`. The Makefile uses this file through the wrapper `docker compose -f srcs/docker-compose.yml`.

Each Dockerfile constructs one service image. Service configuration files define daemon behavior, while each `entry.sh` performs runtime initialization that cannot safely be completed during image build. MariaDB uses `setup.sql` for database/user provisioning. WordPress uses WP-CLI configuration for WordPress automation. NGINX keeps its expected signing key in a separate file used while installing NGINX.

## Design decisions

### Virtual Machines vs Docker

A virtual machine emulates hardware and runs a full guest operating system. Docker containers instead share the host kernel while isolating processes, filesystems, networking, and dependencies at the service level.

Docker suits this project because NGINX, WordPress/PHP-FPM, and MariaDB have separate responsibilities and lifecycles. Each can be built and configured independently, while Docker Compose declares their relationships and starts the entire infrastructure reproducibly. Containers should not be described as equivalent to virtual machines in terms of isolation boundaries; they are a lighter service-deployment mechanism.

### Secrets vs environment variables

The project separates confidential credentials from ordinary configuration.

- Docker secrets hold passwords and are mounted as files inside the relevant containers.
- Environment variables hold non-sensitive settings such as database charset, collation, and service configuration.
- MariaDB receives password-file paths such as `/run/secrets/mariadb_root_password` and `/run/secrets/mariadb_user_password`, rather than receiving those password values as ordinary environment variables.

This avoids baking credentials into Dockerfiles or image layers and reduces the risk of exposing them through configuration dumps or logs.

The Makefile stores generated secret files under `srcs/secrets`. Do not commit these files or place their values in the regular environment configuration. For safe setup instructions, see [Initial configuration](USER_DOC.md#initial-configuration).

### Docker network vs host network

The services communicate through the Docker Compose private network. Compose provides internal service discovery, allowing services to address dependencies by their service names without publishing every port to the host.

Host networking is intentionally not used. It would bypass normal container network isolation and make internal services unnecessarily reachable. NGINX is the controlled ingress point; WordPress/PHP-FPM and MariaDB stay internal.

### Docker volumes vs bind mounts

Persistent storage must outlive individual containers. The infrastructure keeps WordPress files and MariaDB data outside the ephemeral writable layer of each container so that ordinary restarts or container recreation do not require a new WordPress installation or database initialization.

A Docker named volume is managed by Docker, while a bind mount maps a chosen host path into a container. When a local-driver volume is configured with a host device path, it combines Docker's volume declaration with predictable host-backed storage. The exact Compose declarations should be treated as the authoritative storage implementation.

The project uses separate persistent locations for WordPress and MariaDB. Changes to storage declarations, host paths, ownership, or permissions should be tested carefully because they affect initialization and data retention. For safe operational cleanup, see [Persistence and reset](USER_DOC.md#persistence-and-reset).

## Base images and service builds

All mandatory service Dockerfiles use `alpine:3.23` as their base image.

Alpine is used as a minimal base system with a focused package set. It helps keep each image restricted to the packages necessary for its single service responsibility. Its trade-offs matter during maintenance: Alpine uses BusyBox utilities and `musl` rather than glibc, so command behavior, library compatibility, package names, and debugging conventions can differ from Debian-based images.

### NGINX image

The NGINX Dockerfile obtains NGINX from its official repository and verifies the expected NGINX signing key before installation. The expected key is supplied through a bind mount during the build so it is not retained in an image layer.

The image receives the NGINX configuration, security-header configuration, and runtime entry script. The entry script is responsible for runtime work such as TLS material preparation and then launching NGINX in the foreground.

### WordPress image

The WordPress image installs PHP-FPM and a verified WP-CLI package. It includes PHP-FPM configuration, PHP runtime configuration, WP-CLI configuration, and an entry script.

The entry script is responsible for runtime-dependent work: connecting configuration to the initialized database, preserving an existing installation, and starting PHP-FPM as the foreground process. Keep installation state checks idempotent so an existing persistent WordPress directory is not overwritten on every startup.

### MariaDB image

The MariaDB image includes MariaDB, `my.cnf`, `setup.sql`, and its entry script. Database credentials are read from secret-file paths, and the Compose configuration provides a MariaDB health check.

The entry script is responsible for initializing a new data directory only when needed, applying database setup safely, and then starting MariaDB as the container's foreground process.

## Service initialization

### MariaDB

MariaDB initialization must be safe to run against both an empty and an already initialized persistent data directory.

The expected initialization sequence is:

1. Prepare or detect the MariaDB data directory.
2. Start or initialize MariaDB only when no database state exists.
3. Read the root and WordPress-user passwords from their secret files.
4. Apply the database setup SQL.
5. Start MariaDB as the long-running foreground process.

`setup.sql` creates the WordPress database if necessary, creates the configured WordPress database user if necessary, and grants the user privileges for that database. The SQL uses idempotent `IF NOT EXISTS` statements so repeated startup does not recreate existing resources.

### WordPress and PHP-FPM

The WordPress entry script should wait until MariaDB is reachable before attempting first-run configuration. It uses the PHP-FPM and PHP configuration files included in the service and can use WP-CLI to automate WordPress configuration.

On first initialization, the script should create the required WordPress configuration and installation state. On later starts, it must detect the persistent installation and avoid replacing existing configuration, uploads, themes, plugins, or database state. PHP-FPM must remain in the foreground so Docker can supervise the container lifecycle.

### NGINX

NGINX owns the externally reachable HTTPS endpoint. Its configuration defines the virtual host, TLS behavior, document root, security headers, and FastCGI forwarding to the WordPress/PHP-FPM service.

Runtime TLS setup belongs in the NGINX entry script because keys and certificates are runtime environment material. NGINX must be launched in the foreground after configuration succeeds so that the container exits if the web server exits.

## Configuration and secrets

### Environment configuration

Expected location: `srcs/.env` (next to `srcs/docker-compose.yml`). Compose loads that file automatically. `make setup` creates it from the Makefile template: every variable is listed commented out at its default value, grouped into labelled sections (domain, database, WordPress, ports, volumes) so settings are easy to find. Uncomment a line and edit it to override a default.

The same names may also be set in the process environment; a set shell variable overrides `srcs/.env`. Do not put passwords in either place.

`WORDPRESS_DOMAIN` is required (`${WORDPRESS_DOMAIN:?}`). If it is unset or empty, Compose refuses to start. Every other Compose variable has a default in `srcs/docker-compose.yml` and may stay commented out in `srcs/.env`.

Values marked **first install only** are baked into persistent storage. Changing them later has no effect on an already initialized site; a full wipe (`make fclean`, then setup and start again) is required.

| Variable | Default | Change? | Used by | Applied |
| --- | --- | --- | --- | --- |
| `WORDPRESS_DOMAIN` | none (required) | Set to your `login.42.fr` domain | wordpress, nginx | First install (site URL); NGINX vhost on every start |
| `WORDPRESS_DB_NAME` | `wordpress` | Leave default | mariadb, wordpress | First install only |
| `WORDPRESS_DB_USER` | `wordpress` | Leave default | mariadb, wordpress | First install only |
| `WORDPRESS_DB_TABLE_PREFIX` | `wordpress_` | Leave default | wordpress | First install only |
| `DB_CHARSET` | `utf8mb4` | Leave default | mariadb, wordpress | First install only |
| `DB_COLLATE` | `utf8mb4_uca1400_ai_ci` | Leave default | mariadb, wordpress | First install only |
| `WORDPRESS_VERSION` | `7.0.4` | Leave default unless you pin another release | wordpress | First install only |
| `WORDPRESS_TITLE` | `Inception` | Optional site title | wordpress | First install only |
| `WORDPRESS_ADMIN_NAME` | `owner` | Optional; do not use a name containing `admin` | wordpress | First install only |
| `WORDPRESS_ADMIN_EMAIL` | `admin@invalid.email` | Optional dummy address | wordpress | First install only |
| `WORDPRESS_USER_NAME` | `author` | Optional extra user | wordpress | First install only |
| `WORDPRESS_USER_EMAIL` | `author@invalid.email` | Optional dummy address | wordpress | First install only |
| `NGINX_PORT` | `443` | Leave default (published HTTPS port) | nginx, wordpress | First install (site URL); port publish on every start |
| `MARIADB_PORT` | `3306` | Leave default (internal) | mariadb, wordpress | First install only |
| `WORDPRESS_FPM_PORT` | `9000` | Leave default unless it conflicts | wordpress, nginx | Every start |
| `DATA_ROOT_PATH` | `/home/vpoka/data` | Set to your storage parent directory (relocates both drives) | Compose volume devices, Makefile (`setup-dirs` / `rm-dirs`) | Every start |
| `DATA_DRIVE_DIR` | `database` | Set to the directory name of the MariaDB storage | Compose volume `data-drive`, Makefile (`setup-dirs` / `rm-dirs`) | Every start |
| `WEB_DRIVE_DIR` | `website` | Set to the directory name of the WordPress storage | Compose volume `web-drive`, Makefile (`setup-dirs` / `rm-dirs`) | Every start |

The Makefile also reads `srcs/.env` and exports these variables, so `setup-dirs` / `rm-dirs` always operate on the same locations as Compose. `DATA_DRIVE_DIR` and `WEB_DRIVE_DIR` are just directory names inside `DATA_ROOT_PATH`, so the full host paths are `DATA_ROOT_PATH/DATA_DRIVE_DIR` and `DATA_ROOT_PATH/WEB_DRIVE_DIR`. `rm-dirs` removes `DATA_ROOT_PATH` entirely, so no empty parent directory is left behind.

Compose also injects secret *path* variables into containers. These are fixed mount paths, not passwords. Do not set them in `srcs/.env` or the process environment:

| Variable | Value inside the container |
| --- | --- |
| `MARIADB_ROOT_PASSWORD_FILE` | `/run/secrets/mariadb_root_password` |
| `MARIADB_USER_PASSWORD_FILE` | `/run/secrets/mariadb_user_password` |
| `WORDPRESS_ADMIN_PASSWORD_FILE` | `/run/secrets/wordpress_admin_password` |
| `WORDPRESS_USER_PASSWORD_FILE` | `/run/secrets/wordpress_user_password` |

### Docker secrets

`make setup` creates empty placeholder files under `srcs/secrets`. Each file must contain a single password (no extra quotes) before the first start. Compose maps them as Docker secrets; containers see them under `/run/secrets/<secret-name>` (no `.txt` suffix).

| Host file | Compose secret name | Mounted as | Consumed by |
| --- | --- | --- | --- |
| `srcs/secrets/mariadb_root_password.txt` | `mariadb_root_password` | `/run/secrets/mariadb_root_password` | mariadb |
| `srcs/secrets/mariadb_user_password.txt` | `mariadb_user_password` | `/run/secrets/mariadb_user_password` | mariadb, wordpress |
| `srcs/secrets/wordpress_admin_password.txt` | `wordpress_admin_password` | `/run/secrets/wordpress_admin_password` | wordpress |
| `srcs/secrets/wordpress_user_password.txt` | `wordpress_user_password` | `/run/secrets/wordpress_user_password` | wordpress |

A secret should be read from its mounted file by the relevant startup script, held only as long as needed to configure the service, and never printed. Do not use `ARG`, `ENV`, `COPY`, or command-line arguments to embed secret values into an image.

### Cleanup implications

The Makefile separates normal cleanup from full cleanup. `fclean` depends on `clean`, `rm-env`, `rm-secrets`, and `rm-dirs`; it removes environment configuration, secret files, and the persistent storage directories, including their parent directory `DATA_ROOT_PATH`. This is intentional but destructive.

When changing a secret name, environment variable, path, or setup script, update the Compose configuration, consuming entry scripts, Makefile setup/cleanup rules, and both documentation files together.

## Networking and persistent storage

Compose networking provides private service-to-service connectivity and prevents the database and PHP-FPM services from being exposed directly to the host. NGINX is the only ingress service and should be the only service that publishes the project HTTPS port.

The application and database have distinct persistent storage because their data has different ownership, lifecycle, and recovery requirements:

- WordPress storage retains the site files and user-generated content.
- MariaDB storage retains database tables and records.

When diagnosing failures, inspect host-directory ownership and permissions as well as container-side mount paths. A wrong owner or mode can prevent MariaDB initialization or WordPress file updates.

For the Linux hostname mapping required to reach NGINX with the configured domain, see [Configure the local domain](USER_DOC.md#configure-the-local-domain).

## Build and development workflow

The Makefile centralizes Docker Compose usage through:

```make
COMPOSE := docker compose -f srcs/docker-compose.yml
```

The project includes setup, lifecycle, inspection, and cleanup targets. Docker Buildx is part of the required build environment; verify it with `docker buildx version` before diagnosing build issues.

Use this change-impact guide:

| Change | Typical action |
| --- | --- |
| Dockerfile or installed package | Rebuild the affected image, then recreate the service |
| Entrypoint script | Rebuild the affected image, then recreate the service |
| NGINX, PHP-FPM, PHP, or MariaDB configuration | Rebuild/recreate if the config is copied into the image; otherwise restart according to the actual mount strategy |
| Compose environment or secret declaration | Recreate the affected service after validating the new configuration |
| Persistent-data path or volume declaration | Stop the stack and back up data before changing it |

Use the command reference in [USER_DOC.md](USER_DOC.md#operations) for the supported Makefile interface. Do not bypass the setup workflow without understanding which local configuration, directories, and secrets it creates.

## Debugging and maintenance

Start with service status and logs:

```sh
make ps
make logs
```

For targeted maintenance, use the Makefile's execution helpers as documented by `make help`. Investigate problems in this order:

1. Confirm Docker, Docker Compose, and Docker Buildx availability.
2. Confirm required environment configuration and secrets exist.
3. Check container status and logs.
4. Verify NGINX is listening and serving the configured domain through HTTPS.
5. Verify WordPress/PHP-FPM can reach MariaDB by internal service name.
6. Check persistent storage mount paths, ownership, and permissions.
7. Validate that initialization is idempotent and did not attempt to recreate existing state.

Before using any destructive cleanup command, read [Persistence and reset](USER_DOC.md#persistence-and-reset). Back up WordPress files and MariaDB data before changing storage definitions or running a full reset.

## Extension rules

When adding or changing services:

- Give each container one primary responsibility.
- Keep internal-only services off the host network and do not publish ports without a clear requirement.
- Store credentials as Docker secrets, not ordinary environment variables or image content.
- Add persistent storage deliberately and document its ownership, backup, and cleanup behavior.
- Keep entry scripts idempotent for persistent data.
- Treat bonus services as optional and document their activation separately.
- Update `README.md`, `USER_DOC.md`, and `DEV_DOC.md` whenever a change affects the public architecture, user workflow, or configuration contract.
